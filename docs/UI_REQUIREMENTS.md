
# KancControl — Требования к UI/UX-дизайну

## 1. Роль и задача

Выступай в роли Senior UI/UX Designer и Frontend Architect, специализирующегося на разработке современных B2B-систем, SaaS-платформ, административных панелей и мобильных веб-приложений.

Твоя задача — разработать современный, удобный, минималистичный и адаптивный интерфейс для информационной системы **KancControl**.

Главный приоритет — мобильные устройства, поскольку большинство пользователей системы, особенно продавцы, будут работать через смартфоны.

Не создавай десктопный интерфейс, который просто уменьшается под размер телефона. Сначала проектируй мобильную версию, затем адаптируй её под планшеты и компьютеры.

---

## 2. Контекст проекта

KancControl — внутренняя информационная система для розничной сети магазинов канцелярских товаров с несколькими филиалами.

Основная цель — заменить ручную передачу отчетов и заявок через WhatsApp централизованной системой.

Система должна обеспечивать:

- Отправку ежедневных отчетов о продажах и товарах.
- Создание еженедельных заявок на пополнение запасов.
- Отслеживание статусов заявок.
- Одобрение и отклонение заявок администрацией.
- Управление филиалами и сотрудниками.
- Контроль деятельности филиалов.
- Анализ продаж и запасов товаров.

Это рабочий инструмент для бизнеса, а не рекламный сайт.

Интерфейс должен помогать сотрудникам быстро выполнять повседневные задачи, а администраторам — контролировать процессы и принимать решения.

## 3. Технологический стек

В проекте уже используются:

- Next.js
- React
- Bootstrap
- MySQL
- Prisma ORM

Требования к реализации интерфейса:

- Используй существующую интеграцию Bootstrap.
- Используй адаптивную сетку Bootstrap там, где это уместно.
- Применяй CSS Variables для централизованного управления цветами и стилями.
- Используй CSS Grid и Flexbox для построения интерфейсов.
- Используй Bootstrap Icons или уже установленную библиотеку иконок.
- Не добавляй новые UI-фреймворки без обоснования необходимости.
- Не заменяй Bootstrap на Tailwind CSS.
- Не устанавливай лишние библиотеки.

Перед изменением интерфейса изучи структуру существующего проекта и установленные зависимости.

Сохраняй существующую архитектуру, backend, аутентификацию, базу данных и бизнес-логику.

## 4. Визуальный стиль

Основной стиль:

**Modern Bento Grid + Minimalist Enterprise SaaS.**

Интерфейс должен выглядеть:

- Современно.
- Минималистично.
- Профессионально.
- Чисто.
- Спокойно.
- Надежно.
- Понятно для обычного пользователя.
- Подходить для ежедневной работы.

Используй Bento Grid — систему карточек разного размера, объединенных в логические группы.

Однако не нужно превращать абсолютно каждый элемент в карточку. Формы, таблицы, навигация и обычные текстовые блоки должны сохранять подходящий для них формат.

Избегай:

- Чрезмерного использования градиентов.
- Сильных теней.
- Glassmorphism.
- Большого количества декоративных иллюстраций.
- Ненужных анимаций.
- Слишком закругленных элементов.
- Избыточных пустых пространств.
- Перегруженных информацией экранов.
- Мелких элементов управления.
- Декоративных графиков без практической пользы.

Главный приоритет — удобство использования, а не визуальные эффекты.

## 5. Цветовая палитра

Используй единую цветовую палитру.

### Основные цвета

| Назначение | Цвет |
|---|---|
| Основной темно-синий | `#172554` |
| Акцентный бирюзовый | `#0D9488` |
| Фон приложения | `#F1F5F9` |
| Фон карточек | `#FFFFFF` |
| Основной текст | `#0F172A` |
| Второстепенный текст | `#64748B` |
| Границы | `#E2E8F0` |

### Семантические цвета

| Назначение | Цвет |
|---|---|
| Успех | `#16A34A` |
| Предупреждение | `#F59E0B` |
| Ошибка | `#DC2626` |
| Информация | `#2563EB` |

### Правила использования цветов

- Темно-синий используй для брендинга, заголовков и важных элементов навигации.
- Бирюзовый используй для основных кнопок и интерактивных элементов.
- Нейтральные цвета должны преобладать в интерфейсе.
- Семантические цвета используй только для обозначения важных состояний.
- Не обозначай статус только цветом: добавляй текстовую подпись или понятную иконку.
- Обеспечь достаточный контраст текста и элементов управления.

Определи цвета через CSS Variables, чтобы можно было изменить палитру во всем приложении централизованно.

## 6. Mobile-First и адаптивность

Мобильная версия имеет наивысший приоритет.

Проверяй интерфейс на следующих размерах:

- Маленькие смартфоны: 320–375 px.
- Обычные смартфоны: 375–430 px.
- Планшеты.
- Настольные компьютеры.

### Требования к мобильной версии

- Не допускай горизонтальной прокрутки всей страницы.
- Не используй постоянно открытую боковую панель, занимающую место на маленьком экране.
- Используй компактную верхнюю навигацию или другой удобный мобильный вариант.
- Рассмотри нижнюю панель навигации для основных разделов продавца.
- Размещай основные действия в удобной для большого пальца зоне.
- Делай кнопки и интерактивные элементы достаточно крупными.
- Ориентируйся на размер области нажатия не менее 44 × 44 CSS-пикселей.
- Используй читаемые размеры текста. Для полей ввода ориентируйся на 16 px и более.
- Располагай формы преимущественно вертикально.
- Не используй лишние колонки.
- Не делай важные действия зависимыми от наведения курсора.
- Не заставляй пользователя долго прокручивать страницу ради основных функций.
- Обеспечь корректную работу выпадающих меню и диалоговых окон на телефонах.
- Используй адаптивные отступы и размеры текста.

На мобильных устройствах Bento-карточки в большинстве случаев должны располагаться в один столбец.

Две колонки допускаются только тогда, когда содержимое остается читаемым, а элементы управления — удобными.

### Требования к десктопной версии

- Используй боковую панель навигации, которую при необходимости можно сворачивать.
- Предоставляй более широкую рабочую область.
- Применяй Bento Grid для обзорных страниц и аналитики.
- Используй таблицы, когда они действительно упрощают сравнение данных.
- Не растягивай формы и текстовые блоки на чрезмерную ширину.

## 7. Интерфейс в зависимости от роли пользователя

В системе предусмотрены две роли: SELLER и ADMIN.

Для каждой роли необходимо создать отдельный пользовательский опыт.

### Интерфейс продавца (SELLER)

Продавец преимущественно использует смартфон и должен быстро выполнять повседневные задачи.

Главный экран продавца должен содержать:

1. Отправку ежедневного отчета.
2. Создание заявки на пополнение товаров.
3. Просмотр статусов заявок.
4. Историю отчетов.
5. Информацию о своем филиале.

Продавец не должен видеть административную аналитику, конфиденциальную информацию других филиалов и функции управления системой.

Используй понятные названия действий:

- «Отправить ежедневный отчет».
- «Создать заявку».
- «Посмотреть статус заявки».

Не перегружай интерфейс продавца дополнительными разделами и информационными блоками.

### Интерфейс администратора (ADMIN)

Администратор должен управлять бизнесом и контролировать его деятельность.

На главной панели можно разместить:

- Количество филиалов.
- Статистику отправленных отчетов.
- Количество ожидающих заявок.
- Последние действия пользователей.
- Обзор продаж.
- Сравнение филиалов.
- Статистику запасов товаров.

Интерфейс администратора также должен полноценно работать на смартфонах.

В мобильной версии сначала показывай важные показатели и действия. Подробную аналитику и большие таблицы переноси на отдельные страницы или представляй в более удобном формате.

## 8. Dashboard и Bento Grid

Используй Bento Grid преимущественно для главной панели администратора и аналитических страниц.

Возможная структура Dashboard администратора:

- Количество филиалов.
- Отправленные за сегодня отчеты.
- Ожидающие рассмотрения заявки.
- График продаж за выбранный период.
- Сравнение эффективности филиалов.
- Последние действия пользователей.

Используй карточки разного размера только тогда, когда этого требует важность или содержание информации.

Не создавай фиктивную статистику и графики.

Используй реальные данные из backend. Если данных пока нет, показывай понятное пустое состояние с объяснением, почему информация отсутствует.

На мобильных устройствах:

- Располагай карточки вертикально.
- Показывай наиболее важную информацию первой.
- Не используй слишком маленькие графики.
- При необходимости упрощай отображение графиков.
- Предоставляй возможность открыть подробную аналитику на отдельной странице.

## 9. Формы и бизнес-процессы

Формы являются одной из центральных частей KancControl.

Необходимо предусмотреть удобные формы для:

- Ежедневных отчетов.
- Заявок на пополнение запасов.
- Создания учетных записей продавцов.
- Управления филиалами.
- Рассмотрения заявок.

### Требования к формам

- Одна понятная основная кнопка действия.
- Видимые подписи полей.
- Понятные сообщения об ошибках.
- Обозначение обязательных полей.
- Логичная группировка данных.
- Подходящие типы мобильной клавиатуры.
- Числовая клавиатура для количества товаров и денежных значений.
- Понятные состояния загрузки, успеха и ошибки.
- Защита от случайной повторной отправки.
- Сохранение введенных данных при ошибках валидации, если это уместно.

Не используй placeholder в качестве единственной подписи поля.

Не создавай чрезмерно длинные формы. Разделяй сложные формы на логические части.

## 10. Таблицы и списки данных

Большие таблицы неудобны для просмотра на смартфонах.

### Для мобильных устройств

- Предпочитай вертикальные карточки для списков отчетов и заявок.
- Показывай наиболее важную информацию первой.
- Добавляй понятный переход к подробной информации.
- Делай статусы хорошо заметными.
- Не отображай в списке все поля базы данных.
- При необходимости добавляй поиск и фильтрацию.

### Для компьютеров

- Используй таблицы, если они упрощают сравнение данных.
- Следи за читаемостью столбцов.
- Соблюдай единое выравнивание и отступы.
- Не добавляй декоративные столбцы без необходимости.

Не пытайся просто уменьшить большую десктопную таблицу до мобильного размера. Измени способ представления данных, если это необходимо.

## 11. Навигация

Навигация должна быть последовательной и одинаковой по логике на всех страницах.

### Навигация продавца

Основные разделы:

- Главная.
- Отчеты.
- Заявки.
- Профиль.

Для мобильной версии можно использовать нижнюю панель навигации с наиболее важными разделами.

### Навигация администратора

Возможные разделы:

- Dashboard.
- Отчеты.
- Заявки.
- Филиалы.
- Продавцы.
- Аналитика.
- Профиль.

На мобильных устройствах используй компактное меню, выдвижную панель или другой подходящий вариант.

Активный раздел должен визуально отличаться от остальных.

Не показывай пользователю ссылки и действия, которые не соответствуют его роли.

Помни, что скрытие элемента интерфейса не заменяет серверную проверку прав доступа.

## 12. Интерактивность и обратная связь

Каждый интерактивный элемент должен иметь понятное назначение.

Предусмотри состояния:

- Обычное.
- При наведении, если применимо.
- В фокусе.
- Активное.
- Отключенное.
- Загрузка.
- Успешное выполнение.
- Ошибка.

Используй небольшие анимации только тогда, когда они улучшают пользовательский опыт.

После важных операций показывай понятную обратную связь:

- Отчет успешно отправлен.
- Заявка создана.
- Заявка одобрена.
- Заявка отклонена.
- Изменения сохранены.

Не полагайся только на цвет при отображении статусов.

Не используй подтверждающие диалоговые окна для каждого обычного действия. Оставь их для важных или потенциально разрушительных операций.

## 13. Доступность

Соблюдай основные принципы доступности WCAG.

Обеспечь:

- Достаточный контраст цветов.
- Видимое состояние клавиатурного фокуса.
- Семантически правильный HTML.
- Подписи для полей форм.
- Доступные названия кнопок с одними иконками.
- Логичную структуру заголовков.
- Возможность навигации с клавиатуры.
- Обозначение статусов не только цветом.
- Читаемый текст и удобные области нажатия.

Не используй иконки без доступных подписей, если их назначение неочевидно.

Создай переиспользуемые UI-компоненты и стили для:

- Кнопок.

- Карточек.
- Индикаторов статуса.
- Элементов навигации.
- Заголовков страниц.

- Состояний загрузки.
- Сообщений об ошибках.
- Диалогов подтверждения.

Соблюдай единообразие:

- Отступов.
- Типографики.
- Радиусов скругления.
- Цветов.
- Размеров кнопок.
- Стилей карточек.
- Индикаторов статуса.

Не стилизуй каждую страницу независимо от остальных.

Используй CSS Variables и переиспользуемые компоненты там, где это оправдано.

## 15. Правила внедрения дизайна

Перед началом реализации:

1. Изучи текущую структуру проекта.
2. Найди существующие layout-компоненты, страницы и стили.
3. Проверь версию Bootstrap и установленные библиотеки иконок.
4. Изучи существующую аутентификацию и навигацию по ролям.
5. Определи, какие страницы уже реализованы.
6. Предложи последовательный план внедрения дизайна.

Не переписывай приложение целиком.

Не изменяй backend и структуру базы данных ради визуальных изменений без конкретной необходимости.

Внедряй дизайн постепенно.

Для каждой страницы:

1. Объясни предполагаемую структуру интерфейса.
2. Определи компоненты, которые нужно создать или изменить.
3. Реализуй страницу с учетом существующей архитектуры.
4. Проверь отображение на компьютере.
5. Проверь отображение на смартфоне.
6. Убедись, что существующая функциональность и разграничение ролей работают.
7. Исправь проблемы удобства и отображения перед переходом к следующей странице.

Не реализуй все страницы одновременно.

## 16. Итоговая цель

KancControl должен выглядеть как современное профессиональное мобильное бизнес-приложение.

Продавец должен иметь возможность удобно отправлять ежедневные отчеты и создавать заявки непосредственно со смартфона.

Администратор должен иметь возможность контролировать филиалы, просматривать отчеты, одобрять заявки и анализировать деятельность бизнеса без лишней сложности.

Итоговая концепция:

**Mobile-First UX + Bento Grid + Минималистичный Enterprise SaaS + Цветовая палитра Navy/Teal + Адаптивный Bootstrap.**

Главные критерии качества:

1. Удобство на смартфонах.
2. Простота выполнения бизнес-операций.
3. Единообразие интерфейса.
4. Доступность.
5. Адаптивность.
6. Поддерживаемость и простота дальнейшего развития.

Всегда ставь практичность и удобство пользователя выше декоративного оформления.
